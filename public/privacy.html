Deadlight Ops privacy policy

Deadlight Ops is a self-hostable co-op game. This policy describes what the included game software does. The operator of any public installation controls its server and hosting provider; ask that operator about its own contact details and policies before playing there.

Information used

The server generates an anonymous player ID and signs a browser identity token. It stores the ID, chosen username, XP, level-related progress, campaign completions, earned/spent tokens, owned/equipped weapons and cosmetic character outfits, match count, and elimination count in a server-side JSON file. While you play, it holds room membership, position, aim, health, ammo, and other match state in server memory. Players in your room can see your username, a short public ID tag (the first eight characters of your player ID), level, position, health, and combat actions. The full player ID is shown in your operator record and to authorized administrators. Your signed token and cosmetic/quality preferences (including your last entered username, FOV, sensitivity, and mute) are stored in your browser's local storage; a room-closure notice may be stored temporarily in session storage.

If the operator enables administrator password login, the browser sends the entered credentials to the server for verification. The configured account stores a username and salted password hash, not the plaintext password. The game does not save admin passwords or password-session tokens in browser storage. Password sessions are held in server memory for up to 15 minutes and are revoked by logout or disconnect. Sign-in attempt timestamps and connection addresses are held in server memory for rate limiting. Rate-limit records become inactive after one minute and are cleared on subsequent sign-in attempts or a server restart. A browser password manager may separately offer to remember credentials under your own browser settings.

Authorized administrators can search registered profiles by username or player ID, view saved progression even when a player is offline, and grant weapon/map access or change levels. The server keeps up to 1,000 private audit entries for administrator actions, sign-in/session events and rejected commands. Entries contain timestamps, action names, player IDs, room codes, rejection reasons and counts, and assigned levels where relevant. They do not contain passwords, password hashes, identity tokens, IP addresses or raw command payloads. Entries are retained until displaced by newer entries or deleted by the operator; repeated rejections may be aggregated. Only authorized administrators can view these logs. Rejected input is not treated as proof of cheating and does not cause an automatic ban.

On hosts using ephemeral storage, replacing or stopping a replica can erase player records, signing identities and audit logs. The server operator is responsible for choosing persistent storage where retention is required.

Purpose, sharing, and retention

The worldwide leaderboard shares saved usernames, short public player tags, rank, level, XP, elimination count and match count with other connected players on this installation, including while an operator is offline. It offers separate XP and elimination rankings; XP reflects saved progression, including administrator level changes. Empty visitor profiles and practice sessions do not qualify. Rankings are calculated from the existing player records, without collecting location data or contacting an external ranking service. Full player IDs, identity tokens, wallets, inventories and administrator roles are not included in leaderboard responses. Rankings last as long as the underlying player records; ephemeral hosting can erase them.

NPC elimination tokens are credited after a successful server-side save. Failed writes are shown explicitly and retried while the server remains running; unsaved pending rewards exist only in server memory. Outfit purchases use only earned game tokens, not real money. Your equipped outfit ID is shared with room members to render your character; your token balance and owned-outfit collection are not included in public room snapshots. Wallets and purchases can be erased on ephemeral hosting.

Lobby chat is visible only to members of that room and keeps the latest 50 messages, including verified usernames, short public tags and timestamps, in server memory. It is lost when the room is removed or the server stops. Lobby removals are tied to a private player ID within that room, not an installation-wide ban.

Player reports contain the typed reason, reporter and reported player IDs and usernames, room code, arena, game mode, submission time, status, and administrator reviewer ID/time. When a verified connection address is available, a keyed hash of the reported player's IP address is also captured for manual IP moderation, not the raw address. They are stored privately in reports.json; only authorized administrators can list or review them, without seeing address hashes. The latest 500 reports are retained until displaced by newer submissions or deleted by the operator. Reporting is rate limited using these retained records. Reports are claims, not proof, and never automatically punish a player. Do not include personal information in chat or report reasons. Ephemeral hosting can also erase reports.

Authorized administrators can manually ban a reported operator identity or the exact reported IP address, and remove bans. Bans disconnect matching players and refuse new game connections until removed or expired; an IP ban can affect innocent players sharing a network. Up to 5,000 active bans are retained privately in bans.json, containing a ban ID, type, player ID or keyed address hash, reported username, source report ID, administrator ID, reason, timestamp and optional end time. The separate private moderation-secret keys the hashes. Hashes are pseudonymous data, not anonymous data; raw IP addresses and hashes are not shown in the admin panel or audit logs. Temporary bans expire automatically; permanent bans persist until removed or the operator deletes the data. Ephemeral hosting can erase bans, reports and their key. Clearing browser storage or changing networks may bypass anonymous-identity or address bans.

The ban screen's Contact / Appeal ban form sends your explanation privately to authorized administrators, even while game access is blocked. The server matches your signed browser identity or verified connection address to the current ban. Each ban accepts one appeal; repeat submissions do not create additional requests. Up to 500 appeal records are stored in ban-appeals.json, containing the banned player ID and username, ban ID/type/reason/start/end times, appeal explanation and submission time, decision, and administrator reviewer ID/time. Reviewed records may be displaced when the inbox is full; open requests are kept until reviewed or deleted by the operator. IP appeals concern the shared address and do not prove who sent them. Submission attempt counters use keyed address hashes in memory, expire after one minute, and are cleared on a server restart. Only authorized administrators can read the inbox and approve or reject requests; approval removes only the appealed ban, not other active bans. Do not include passwords or personal information in your explanation. Ephemeral hosting can erase appeals. Contact the operator directly for data-deletion requests.

The existing private password login grants a temporary owner session. Only that owner session may ban administrators; identity-allowlisted administrators alone cannot. Reports also record whether the target had administrator access at submission so this protection remains after disconnect. Self-bans and IP bans affecting the acting moderator's own connection are blocked. A ban blocks the matching identity/address from both gameplay and password sign-in; recovery requires an unbanned owner session or operator intervention.

These details enable matchmaking by room code, co-op combat, the armory, campaign rewards, and saved progression. No analytics, advertising, third-party login, or paid token service is included. The game does not intentionally send player records to an asset CDN. A public host or reverse proxy may process your IP address and connection metadata under its own policies. The included software keeps player records and the token-signing secret until the server operator deletes them; there is no automatic expiration, self-service deletion, or account recovery. Active rooms exist only until the process stops or the room is closed. Clearing browser data removes your local identity token but does not delete the server record and will lose access to that progress.

Choices and security

The Halloween decorations-and-lights preference and the last dismissed What's new release ID are saved only in your browser's local storage. The update waiting-room target challenge keeps its score only in page memory for this visit; it does not submit scores, award progression or save personal data. Seasonal scenery uses bundled procedural geometry and does not send preference or location data to an external service.

Choose a non-identifying username; usernames are unique for each installation and can be changed when entering a room. Do not share your identity token. Your public ID tag is not a login credential. Ask the operator of your deployment to delete a server-side record or answer a privacy request; for local installations, the operator can remove the relevant entry from players.json while the server is stopped. Protect the data directory and signing secret and use HTTPS for public hosting. A browser token is a bearer credential, not an account password.
